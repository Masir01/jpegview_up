## JPEGView 删除文件后跳下一张比翻页慢的根因（代码确认）
删除命令 IDM_MOVE_TO_RECYCLE_BIN 流程（MainDlg.cpp:1447-1453）：
`GotoImage(POS_AwayFromCurrent, NO_REQUEST)` → `DeleteFile(SHFileOperation 同步)` →
`Reload(NULL, false)` → `GotoImage(POS_Current)`。
三条额外开销叠加，翻页(IDM_NEXT→GotoImage(POS_Next))完全没有：
1. 主因 `Reload(NULL,false)` 第三参 hCallbackWnd=NULL → FileList.cpp:304 走 `FindFiles()`
   同步枚举+排序整个目录，阻塞 UI 线程（HDD/USB/网络盘/多文件尤慢）。
2. read-ahead 缓冲未命中：NO_REQUEST 在 MainDlg.cpp:2538 提前 return 跳过预解码；
   Reload 重建列表；最终 POS_Current 现场解码下一张（翻页则命中后台预解码缓存，
   JPEGProvider.cpp:56 StartNewRequestBundle 早已解码好 N+1）。
3. SHFileOperation(FO_DELETE|FOF_ALLOWUNDO) 移回收站是同步 I/O。
优化方向（未实施）：删除后仅就地 erase m_fileList 项而非 FindFiles 全扫；或删除前
去掉 NO_REQUEST 让后台先预解码下一张。

## 删除延迟优化已实施（就地移除 + 异步重载）
改动 3 文件，x64 Release 编译通过（仅 PostBuildEvent 复制 DLL 报路径找不到，与改动无关）：
- FileList.h: 新增 `void RemoveFile(LPCTSTR fileName);`
- FileList.cpp: 实现 RemoveFile —— 按文件名(_tcsicmp GetTitle)从 m_fileList erase，
  再 `m_iter=FindFile(sCurrentFile)`、`m_iterStart=wrap?m_iter:begin()` 重置迭代器，
  不触发任何目录扫描（vector erase 使所有迭代器失效，故必须重算 m_iter）。
- MainDlg.cpp:1449-1454 删除流程：
  `DeleteFile` → `fileListOfDeletedImage->RemoveFile(currentFileName)`（即时移除）→
  `DeleteHistory` → `Invalidate` → `GotoImage(POS_Current)`（立即落在有效下一张）→
  `Reload(NULL,false,m_hWnd)`（异步 FindFilesAsync 后台重扫以纳入其他进程新增文件）。
关键安全性：OnScanCompleted(FileList.cpp:1116) 按当前文件名保留位置再 swap 扫描结果，
故异步重载不会打乱当前显示；且 CDirectoryWatcher 监控线程对删除本身也会发变更消息，
双重保障新增文件检测。原同步 Reload 阻塞 UI 的根因已消除。

## 删除后滚轮翻页"不响应"回归 —— 根因与修复（CancelScan UI 阻塞）
【现象】改异步重载后，删除文件后滚轮翻页失灵。
【根因】`FindFilesAsync`(FileList.cpp:1124) 启动前调 `CancelScan()`，`CancelScan`(1113)
在 UI 线程 `WaitForSingleObject(m_hScanThread, 5000)`，最多阻塞 5 秒。删除路径显式
`Reload(m_hWnd)` 起扫描 A；SHFileOperation 移入回收站触发 FILE_NOTIFY_CHANGE_FILE_NAME，
CDirectoryWatcher 约 500ms 后 `OnActiveDirectoryFilelistChanged`(1040) 在
`ReloadWhenDisplayedImageChanged` 开启时再 `Reload(m_hWnd)` → 第二次 `FindFilesAsync`
→ `CancelScan` 在 UI 线程等扫描 A 结束 → 滚轮卡死。
【修复】删除路径改为：仅当 `!ReloadWhenDisplayedImageChanged()` 时才显式异步重载；
开启时交给 CDirectoryWatcher 自己异步重扫（只扫一次，不撞车）。删一次只扫一次，
消除 UI 阻塞，仍保留新增文件检测。x64 Release 编译通过（仅 PostBuildEvent 复制 DLL
路径问题，与改动无关）。
【注意】`CancelScan` 的 `WaitForSingleObject` 在 UI 线程是潜在隐患，若未来出现其他
重叠扫描场景仍可能卡 UI；根本修法应让 CancelScan 非阻塞，但本次用条件分支最小修复。

## dev-hw 解码比官方"慢很多"根因（线程优先级）
【现象】dev-hw 分支解码/翻页比官方(sylikoly 原版)慢很多。
【根因】`WorkThread.cpp:87` 我们(commit 14e6065)主动 `SetThreadPriority(THREAD_PRIORITY_BELOW_NORMAL)`
给所有解码/重采样工作线程降 CPU 优先级，换取 UI 流畅；官方原版无此调用(默认 NORMAL)。
解码是 CPU 密集，CPU 竞争时 BELOW_NORMAL 让出 → 解码吞吐下降 → 比官方慢。
函数注释称"I/O 优先级不变故加载速度不受影响"只对磁盘读成立，对解码(CPU)是误导。
【非差异项】NUM_THREADS=1/READ_AHEAD_BUFFERS=2(MainDlg.cpp:68-69)、处理池核心数-1
均与官方一致；FastJPEGDecode/FastRAWDecode 默认 false 官方也关。
【次要差异】dev-hw 移植给 PSD(Lab)/RAW 加了 LCMS 逐像素转换，仅少数格式慢，JPEG/PNG 不走 LCMS。
【修复选项】①追平官方：WorkThread.cpp:87 改 THREAD_PRIORITY_NORMAL 或删该行；
②超官方：FastJPEGDecode=true+FastRAWDecode=true；③根本加速：加 JPEG scale_denom 缩放解码(Wrapper层,零SDK改动)。
【权衡】降优先级是"UI流畅 vs 解码速度"取舍，非bug；用户重视解码速度时应改回 NORMAL。

## JPEGView 扩展支持 DDS 可行性分析（2026-08-03）
【结论】很容易，两条路线：
【路线A 纯配置零编译】JPEGView 已有 IF_WIC 通道。Windows 8+ 系统 WIC 内置 DDS 解码器。
改 JPEGView.ini：WICPriority=1 + FilesProcessedByWIC 加 *.dds 即可。链路：
GetImageFormat(ImageLoadThread.cpp:40-48 / Helpers.cpp:778)→IF_WIC→ProcessReadWICRequest
(ImageLoadThread.cpp:354-357,1063-1076)→LoadImageWithWIC(WICLoader.cpp)。
文件浏览器自动纳入(FileList.cpp:183-186 追加 FilesProcessedByWIC)。
【路线A硬限制】①WICLoader.cpp:98 转 GUID_WICPixelFormat32bppBGR 丢弃 Alpha(游戏贴图致命)；
②WIC DDS 解码器仅支持部分 DXGI 格式(BC1-7 在 Win10 较全,旧版更少,legacy/10:10:10:2 失败)；
③只取第0帧,无 mip/cube/数组。
【路线B 专用解码器】仿 PSDWrapper/RAWWrapper + 微软 DirectXTex(MIT,全格式+Alpha+mip/cube)。
加 IF_DDS(ImageProcessingTypes.h:43)、magic-byte "DDS "=0x44445320 检测(ImageLoadThread.cpp:37)、
新增 DDSWrapper.cpp/.h、ProcessRequest/InvalidateDecoderCaches 加 IF_DDS 分支(参 IF_PSD)、
FileList.cpp:131 csFileEndingsInternal 加 "dds"。难度约1-2天,无架构风险。
【建议】仅看一眼用路线A；作游戏贴图查看器需Alpha/BC用路线B。

## 删除后"卡列表/无法切换下一张"二次回归修复（幽灵项竞态）
【现象】199d8c2d(删除延迟优化) 后，连删几个文件有几率卡列表——无法切下一张，但 UI 不卡死。
【根因】删除走 `RemoveFile` 就地 erase(瞬时无卡顿)，但 CDirectoryWatcher 的 `FILE_NOTIFY_CHANGE_FILE_NAME`
变更消息 → `OnActiveDirectoryFilelistChanged`(MainDlg.cpp:1040) → `Reload(m_hWnd)` → 异步
`FindFilesAsync` → `OnScanCompleted`(FileList.cpp:1143) 用磁盘扫描快照**整体 swap** 替换 m_fileList。
目录监控线程有 `WaitForSingleObject(m_terminateEvent,500)`(DirectoryWatcher.cpp:139) 节流，连删时
只跑一次扫描，而这次扫描捕捉的是"旧目录快照"(删除尚未完全刷盘/或在多次删除之间启动)，
把已删文件当**幽灵项**加回列表。之后翻页落到幽灵项 → RequestImage 加载失败 → 画面不变 → 表现为卡死。
【修复】FileList 新增 `std::set<CString> m_deletedFiles`(按完整路径,避免跨文件夹同名误删)：
- `RemoveFile`(FileList.cpp:360) 中 `m_deletedFiles.insert(fileName)` 记录已删完整路径；
- `OnScanCompleted` swap 后，若集合非空则遍历 erase 掉 GetName() 仍在集合中的项，再 `clear()`。
  这样陈旧扫描重新加回的已删文件被剔除，导航不再落到幽灵项；集合按绝对路径精确剔除，
  不影响其他文件夹同名文件；`FindFile(sCurrentFile)` 在剔除后重算 m_iter(当前文件非已删项,必命中)。
【线程安全】RemoveFile 与 OnScanCompleted 均在 UI 线程；m_scanResult 后台线程只写扫描结果不碰本集合，无竞态。
【验证】x64 Release 编译通过(0 error,仅既有 warning)；逻辑覆盖"连删→单扫描快照→幽灵项"场景。
【注意】`CancelScan` 的 `WaitForSingleObject(m_hScanThread,5000)`(FileList.cpp:1113) 仍在 UI 线程，
若未来再有重叠扫描场景可能卡 UI；本次用"幽灵项剔除"最小修复，未动 CancelScan。
