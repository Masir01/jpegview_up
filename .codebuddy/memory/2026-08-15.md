## 降采样提交安全与生产级审查结论（2026-08-15）

用户要求审查 fee8bcd（超大 JPEG 降采样解码）是否新增漏洞/满足生产级标准。源码级核查结论：

【内存安全：无漏洞，关键点逐一验证】
1. **TJSCALED 3.x 为 ceil 非 floor**（turbojpeg.h 注释明确 `ceil(dimension * scalingFactor)`），与 `jpeg_core_output_dimensions`（jdmaster.c）实际输出公式完全一致（1/2→ceil(w/2)、1/4→ceil(w/4)、1/8→ceil(w/8)）→ 分配尺寸=解码输出尺寸，无越界
2. **lossless JPEG 缩放被库忽略**（jdmaster.c lossless 分支硬编码 output_width=image_width），但 `tj3Decompress8`（turbojpeg-mp.c:230-231）在 jpeg_start_decompress 后校验 `pitch >= output_width*pixelSize` 会 THROW → 安全拦截，不写 buffer
3. **FindDownscaleFactor 只产生 {1,2}/{1,4}/{1,8}**（GetInt clamp [2,8] + nDenom*=2），全在 tj3SetScalingFactor 支持列表内，不会失败
4. **int 溢出**：`<=MAX_IMAGE_PIXELS`(x64 5.24e8)成立时 TJPAD(3w)*h≤~1.57e9<INT_MAX；极端超限时 nothrow new 兜底 → outOfMemory 安全拒绝
5. 其余 3 个 ReadImage 调用点（dcraw_mod:10656/RAWWrapper:79/PSDWrapper:508）不传 pScaleDenom 向后兼容

【生产级缺陷】
- **【高】降采样图保存丢分辨率**：SaveImage(bFullSize=true)（SaveImage.cpp:362-363）用 `pImage->OrigSize()`=降采样尺寸；`IDM_SAVE_ALLOW_NO_PROMPT`+SaveWithoutPrompt（MainDlg.cpp:1403）`SaveImageNoPrompt(CurrentFileName(false), true)` **静默覆盖原文件为 1/N 分辨率 → 永久数据丢失**。无损变换（JPEGLosslessTransform）基于文件流不受影响。修复建议：保存前检查 GetDownsampleFactor()>1 提示/禁用
- **【中】降采样信息未全链路传播**：PSD/RAW/dcraw 内嵌 JPEG 超大时也会降采样且调用方无感知（PSD 合成尺寸可能错位）
- **【低】abs((double)w*h)**（TJPEGWrapper.cpp:67/84）：int 版 abs 收 double，超 INT_MAX 时 double→int 转换 UB（沿用旧写法，nothrow 兜底不可利用），应改 `(double)w*h<=MAX_IMAGE_PIXELS` 直接比较
- **【低】tj3SetScalingFactor 返回值未检查**（防御性；实际不会失败）
- **【低】lossless 超大图**：降采样无效→pitch 检查报"Invalid argument"→显示解码失败而非"图太大"

【结论】无新增可利用内存漏洞；存在 1 个真实数据安全缺陷（降采样保存），需修复后达生产级。

## 降采样策略决策（2026-08-15）

## exiv2 集成性能影响分析（回答用户提问）

用户问 exiv2 集成是否严重拖慢 JPEGView 打开速度。代码确认后结论：**没有严重拖慢**。

- 关键链路：`RequestImage`(JPEGProvider.cpp:34) 在 pRequest->Ready 为 false 时 `WaitForSingleObject(EventFinished, INFINITE)` 同步等待（UI 线程），解码在后台工作线程(ImageLoadThread)执行。`CJPEGImage` 构造(JPEGImage.cpp:86) → `new CEXIFReader` → EXIFReader.cpp:341 `ParseWithExiv2()` → `ExifParser::decode` 全量解析，**发生在后台线程**，与解码串行叠加，不额外阻塞 UI。
- 量化：手写解析(读~15字段) 几十µs；exiv2 全量解析(建 ExifData/Exifdatum 树) 0.1~1ms（APP1 块 8~30KB）；相对 12MP JPEG 解码 50~200ms，占比 <1%。
- 启动开销：exe +1.4MB(~4.5→5.9MB，静态链接 exiv2+tags 表)，启动多加载几百KB~1MB 代码页，SSD 1~5ms 无感知。
- 内存：每图多一棵 ExifData 树（几KB~几十KB）。
- 缓存命中不重复解析（RequestImage 直接返回 Image），read-ahead 预取在空闲线程不阻塞 UI。
- 极端优化选项（懒解析：仅在 F2 面板弹出时才 decode 全量）收益 <1ms，不值得做。

## 打不开 Google Art Project《巴别塔》原画的原因（诊断结论）

用户报告 JPEGView 打不开 `Pieter_Bruegel_the_Elder_-_The_Tower_of_Babel_(Vienna)_-_Google_Art_Project` 原画。规格确认：30000×21952 像素（约 6.59 亿像素），202.82 MB JPEG（nbfox.com 数据）。

根本原因：**像素总数超过 MAX_IMAGE_PIXELS 上限**（MaxImageDef.h:49 x64=500M/约5.24亿、x86=100M/1.05亿）。
- TJPEGWrapper.cpp:42 `if (abs((double)width*height) > MAX_IMAGE_PIXELS) outOfMemory=true` → ReadImage 返回 NULL
- ImageLoadThread.cpp:557 置 request->OutOfMemory=true → 界面显示 FileLoad_OutOfMemory
- 6.59亿 > 5.24亿（x64）→ 即使 x64 也打不开；x86 更双重超限（202MB>50MB MAX_JPEG_FILE_SIZE + 6.59亿>1.05亿）
- 文件名无扩展名时 GetImageFormat 返回 IF_Unknown（Helpers.cpp:784）走 GDI+ 分支，ConvertGDIPlusBitmapToJPEGImage（ImageLoadThread.cpp:153）同样按 MAX_IMAGE_PIXELS 拒绝

设计原因：解码 6.59 亿像素 BGR 需 ~2GB 原始缓冲 + CJPEGImage 复制一份，防 OOM。解决途径：加 .jpg 扩展名无用（像素仍超限）；需缩小到 524M 像素内或用支持超大图的工具。

## 大图内存开销与各软件策略对比（补充问答）

全量解码内存是物理必然：30000×21952 RGB(24bit)≈1.88GB、RGBA≈2.5GB，JPEGView 因 CJPEGImage 复制实际 ~3.8GB。各软件策略分三类：
- **拒绝型**：JPEGView（MAX_IMAGE_PIXELS 预判拒绝）、Windows 经典照片查看器（报"内存不足"，网络确认）
- **硬扛型**：Photoshop CS5 64位（文档~2GB+暂存盘，峰值4~8GB）、IrfanView 64位（官网明示 32 位版受 RAM 限制）、GIMP/FastStone
- **降采样/瓦片型**：现代 Windows Photos（WIC 自动降到屏幕分辨率，内存~几十MB）、XnView MP（设置项）、Google Art Project 网站（瓦片服务器，只看视口）
结论：JPEGView 行为是合理设计取舍（预判拒绝防 OOM），非缺陷。升级方向是加 scale_denom 降采样解码（1/8 时该图只需 ~30MB）。

### "放大到 100% 时局部高清解码"可行性分析

用户设想：降采样 1/N 后，放大到 ≥100% 时按视口对可见区域做**原始分辨率局部解码**（类似瓦片/虚拟内存加载），弥补降采样丢细节。分析结论：

**原理可行（库支持）**：libjpeg-turbo 3.x `tj3SetCrop`（TJPARAM_CROPX/CROPY/CROPW/CROPH，须 4:2:0 用 MCU 对齐）可对 JPEG 矩形区域独立解码，正是"局部高清"所需的原语。

**但 JPEGView 当前架构不满足（高复杂度）**：
1. **CJPEGImage 单缓冲模型**：一张图只有一份 m_pDIBPixels 全图缓冲，无"局部覆盖/混合"层。放大时要么整体重解码，要么维护一块局部高清图 + 视口映射，需要新增多分辨率瓦片缓存层（DIB 分层）。
2. **同步解码链路**：RequestImage→WaitForSingleObject 同步等待（JPEGProvider.cpp:34），局部解码若同步则 UI 卡顿；异步局部解码需引入"视口变化→发起局部解码→就绪回调→重绘"状态机，涉及取消/竞态（翻页、快速缩放时大量取消）。
3. **缩放显示管线**：PaintMemDCMgr 从单张全图按 zoom 拉伸，局部高清需"低清底 + 高清瓦片叠加"双缓冲绘制（与 cross-fade 方案同理，内存翻倍）。
4. **MCU 对齐裁剪**：tj3SetCrop 要求 4:2:0 时 X/Y 对齐到 MCU 块（16/8px），非 4:2:0 限制更严，边缘需扩边重算，视口连续滚动时瓦片边界刷新有锯齿/闪烁风险。

**结论**：技术上可行，但属**架构级改造**（多分辨率瓦片缓存层 + 异步局部解码状态机 + 双缓冲混合绘制 + 裁剪对齐），工作量与 Direct2D 重构同级，风险高。对 JPEGView 的价值：仅降采样打开的大图（用户主动或超大图）在放大时能看局部原像素。

**更经济的中间档**（若要做）：放大 ≥100% 时**整图按需升采样重解码**——视口缩小时整体用更小 denom 重解码一次（非瓦片），实现简单（复用现有 ReadImage 换 denom + 重触发），但超大图全量 1:1 解码内存仍回到 1.88GB，失去降采样意义；仅适合"局部高清但不看全图"时。**终极方案仍是瓦片虚拟内存**（像 Art Project），工作量最大。
